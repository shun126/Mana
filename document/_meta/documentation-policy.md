# Mana ドキュメント執筆方針

このファイルはドキュメント編集者向けの方針です。GitHub Wiki へ公開する本文には含めなくても構いません。

## 目的

Mana のドキュメントは、次の2つを両立させます。

1. Mana やプログラミングに慣れていない読者が、順番に読んで使えるようになること
2. 経験者が、必要な仕様を短時間で正確に調べられること

そのため、入門用の説明と仕様リファレンスを同じページへ詰め込みません。

## ドキュメントの分類

### Getting Started

初めて Mana に触れる人向けです。ソースコード、テキストファイル、コンパイル、VM など、経験者には当たり前の用語も初出時に説明します。

### Tutorial

実際に動く Mana コードを書きながら学びます。最初に Actor / Action / Request を体験し、その後で変数、条件分岐、繰り返し、関数などを学びます。

### Concepts

Mana 固有の考え方と実行モデルを説明します。Request、Priority、スケジューリング、待機、同期などを、個別の構文ではなく相互関係として説明します。

### Reference

正確さと検索性を優先します。概要、構文、詳細仕様、制約、例、関連項目を基本構成とします。

### Integration

Mana Compiler と Mana VM をホストアプリケーションへ組み込む開発者向けです。C++ API、Program Image、native 関数、SourceResolver、Diagnostics などを扱います。

## 説明の原則

- 初学者向けページでは、未説明の専門用語をできるだけ使わない
- 一度に多くの構文を紹介しない
- Tutorial では最小限の機能から動く結果を確認する
- Concepts では「なぜその仕組みがあるのか」を説明する
- Reference では初心者向けの説明を繰り返しすぎず、仕様を明確にする
- 実装と文書が異なる場合は、現行実装を確認してから文書を更新する
- 「工事中」「仕様検討中」の機能は安定仕様の Reference に混ぜない

## コード例

コード例は可能な限り、その時点の Mana Compiler でコンパイルできる内容にします。

将来的にはドキュメント中の実行可能な Mana コードを CI で検証し、言語変更によるサンプルの陳腐化を検出できるようにします。

## GitHub Wiki との共有

リポジトリの `document` を原本とします。

GitHub Wiki へコピーすることを考慮し、ページのファイル名はディレクトリを除いても識別しやすい名前にします。例えば `tutorial-request.md`、`reference-request.md` のように用途を接頭辞で区別します。

Wiki では物理的なディレクトリ構造より `_Sidebar.md` を使ったナビゲーションを優先します。
